BusFactor · technical brief · Anthropic hackathon build

The knowledge that dies when an engineer quits — found, extracted, verified.

Every codebase has modules only one person truly understands. BusFactor computes exactly where that risk lives from git history and the dependency graph, interviews the owner with an agent that has read the code, and refuses to ship the resulting docs until a fresh "new hire" agent can pass an onboarding exam using the docs alone.

01 · the problem

Bus factor is real, and every fix for it fails the same three ways

The "bus factor" is the number of people who can be hit by a bus before a project is in serious trouble. For most modules in most codebases, that number is one. The what of code is in the repo; the why — the rejected alternatives, the incident that motivated the retry logic, the invariant nobody wrote down — lives in one engineer's head. When they leave, incidents follow.

Teams know this. Their countermeasures fail in three specific places:

They can't locate the risk. "Ask around about who knows what" doesn't scale and misses the quiet dependencies. The signal is sitting in git history, unread.
They can't extract the knowledge. "Document your work before you leave" produces a rushed page of what the code already says, because the departing engineer doesn't know which of their thousand assumptions a newcomer will actually trip on.
They can't tell if docs work. Documentation has no test suite. A doc that reads well and a doc that transfers understanding look identical until someone new needs it at 2 a.m.

BusFactor attacks all three — with math, an interviewer, and an exam.

02 · the workflow

Pipeline: from a repo URL to docs that provably work

The order matters. Locating risk is a measurement problem, so it's solved with measurements — parsing git log --numstat, building the import graph, computing three numbers per module. The expensive, fallible instrument (a frontier model) is spent only where it's irreplaceable: asking good questions, judging answers, and writing prose.

03 · the algorithm

Three signals, one honest score

Signal 1 — Knowledge concentration C(m): a recency-weighted HHI

For every module, each commit credits its author with weight that decays with a 180-day half-life — knowledge fades, and the person who wrote a file in 2016 is not its owner today. Damping by 1 + ln(1 + lines) (capped at 400 lines per touch) stops one mega-refactor from counting as years of stewardship. Recency is measured against the repo's own newest commit, so archived projects are judged on their own timeline.

w(commit) = 0.5age/180d · (1 + ln(1 + lines))
sharea(m) = Σ w(commits by a) / Σ w(all commits) — author a's slice of living knowledge
C(m) = Σa sharea² — Herfindahl–Hirschman index, 0→1
effective owners = 1 / C(m)

Signal 2 — Criticality K(m): PageRank over the dependency graph

Concentration alone over-ranks someone's pet utility folder. What makes concentrated knowledge dangerous is that other code depends on it. The analyzer parses static imports (JS/TS/Python — resolving relative specifiers file-by-file), collapses them to module-level edges, and runs weighted PageRank (damping 0.85): a module is critical when many modules depend on it, especially when those modules are themselves critical. Where a repo's language isn't covered by the import parsers, the graph falls back to co-change coupling — modules repeatedly modified in the same commit are structurally entangled, whatever the language.

Signal 3 — Activity A(m): recency-weighted churn

A frozen module can wait for archaeology; a hot one cannot. Recency-weighted lines-changed says how alive each module is right now.

The product form is the point: risk requires all three. One owner on a module nothing imports and nobody touches is trivia. Sixteen owners on the hottest, most-imported module is health. One owner, high centrality, active churn — that's the red square on the map. The kind-weight came out of testing against real repos: express's test suite is 98% one person's recent work, and an unweighted model ranks it above the production core. True, but not what you page someone about — so production code outweighs tests, examples, and docs.

04 · the problem-solving method

Documentation with a unit test

Everything after the risk map exists to defeat one failure mode: AI-written docs that look complete and aren't. The design borrows the oldest trick in measurement — never let the thing being evaluated grade itself.

Three separations make the loop honest:

The exam is written before the interview, straight from the code — so the interviewer can't (even accidentally) teach to the test.
The examinee is context-free. A separate model instance that has never seen the code or the transcript answers with the docs alone — exactly the epistemic position of a real new hire at 2 a.m.
The grader holds the ground truth. It scores substance (correct / partial / wrong) and, crucially, emits gap topics — which feed straight back into the interviewer as the next round's agenda.

The loop converges or stops honestly: pass at ≥ 80%, or after three rounds the docs ship with their score attached — a known-coverage number instead of false confidence.

why the interview asks good questions
The interviewer isn't prompted with "ask about the module." It explores with read-only tools first — git log per file, suspicious commits via git show, greps for HACK/TODO/magic constants — and is instructed to ground every question in something concrete it found: an asymmetry between sibling code paths, a constant with no comment, a commit that landed three days after a revert. The owner answers why; the agent already knows what.

06 · tech stack & model lineup

Cheap math where math works, frontier model where it counts

LayerChoiceWhy
Analysis engine Node + TypeScript, execFile'd git HHI, PageRank (power iteration), churn — deterministic, seconds, zero tokens
Server Express, SSE event stream Interview progress streams live to the browser; sessions in memory
Frontend React 19 + Vite, d3-hierarchy SVG treemap (size = LOC, color = validated sequential ramp), tooltips, owner bars
Interviewer / examiner / docs claude-opus-4-8 Tool-runner agent loop over read-only repo tools; adaptive thinking; the judgment-heavy seat
"New hire" examinee claude-sonnet-5 Deliberately a different, fresh model instance — answers from docs alone
Grader claude-haiku-4-5 Structured verdicts against supplied ground truth — high volume, low cost
Structured everything zod schemas + structured outputs Exams, verdicts, questions all schema-validated — no regex parsing of prose
Agent safety path-confined, read-only tools Canonicalized paths inside the clone; execFile (no shell); output truncation caps

The agent tools are the product's edge: list_files, read_file, grep_repo, git_log_file, git_show — enough for the interviewer to behave like a senior engineer doing archaeology, and nothing that can write, execute, or escape the clone.

07 · run it

Two commands

cd busfactor
npm install
npm start                          # risk map needs nothing else — open http://localhost:5177

export ANTHROPIC_API_KEY=sk-ant-…  # enables interview → docs → exam
npm start

Known limits, stated plainly: import-graph parsing covers JS/TS/Python (other languages fall back to co-change coupling automatically); author identity is keyed on git author name without merging; sessions are in-memory; public repos only. Next steps that fit the architecture: opening the finished docs as a pull request, org-wide scheduled scans, and identity merging via .mailmap.
